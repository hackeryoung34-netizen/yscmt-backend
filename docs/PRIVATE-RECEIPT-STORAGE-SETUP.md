# Private receipt storage setup (preview only)

The Student Portal uses an S3-compatible private object store for bank-transfer receipts. The Django API creates a short-lived presigned upload form, verifies the uploaded object server-side, and creates a short-lived attachment-only download URL.

## Required environment variables

Set these only in the non-production preview service's secret environment. Do not commit values or paste credentials into GitHub issues, chat, or source files.

| Variable | Purpose |
|---|---|
| PORTAL_STORAGE_ENDPOINT_URL | Provider's S3-compatible endpoint |
| PORTAL_STORAGE_ACCESS_KEY_ID | Restricted bucket access key |
| PORTAL_STORAGE_SECRET_ACCESS_KEY | Matching secret |
| PORTAL_STORAGE_BUCKET | Private receipt bucket name |
| PORTAL_STORAGE_REGION | Provider's signing region |

For Cloudflare R2, the endpoint is the account's R2 S3 endpoint and the region is auto. Existing PORTAL_R2_* variable names remain supported for compatibility, but the generic PORTAL_STORAGE_* names are preferred.

## Bucket and access policy

- Create a dedicated bucket for preview receipts; do not reuse a public website-assets bucket.
- Keep the bucket private. Do not enable public read access or public object URLs.
- Use a bucket-scoped key with only the permissions needed to upload, inspect, and download receipt objects.
- Configure browser CORS for the exact preview frontend origin only. Allow only the upload method used by the provider's presigned form (POST), and GET/HEAD only if the browser needs them. Allow Content-Type and x-amz-meta-owner-id request headers and expose only ETag if required.
- Never use wildcard origins with credentials or expose storage access keys to the frontend.
- Verify provider support for presigned POST policy conditions, object metadata, ranged reads, and presigned GET before enabling it. S3-compatible providers do not all implement every feature identically.

## Application safeguards

- Upload authorization is short-lived and tied to the authenticated student's own payment submission.
- The object key is generated by the server; clients cannot choose arbitrary keys.
- The presigned form constrains MIME type and maximum byte size.
- Finalization checks object length, declared MIME type, owner metadata and file signature (PDF/JPEG/PNG).
- Admin downloads use a short-lived signed GET URL with private/no-store cache control and attachment disposition.
- If the provider credentials are absent or object verification fails, the API fails closed. It does not fall back to public storage.

## Verification checklist

1. Configure secrets in a non-production preview environment only.
2. Use a synthetic PDF/JPEG/PNG with no real bank or student details.
3. Verify a student can upload only their own receipt and cannot finalize another student's key.
4. Verify wrong MIME, forged file signature, oversized object and wrong owner metadata are rejected.
5. Verify the download URL expires and cannot be used to list the bucket.
6. Confirm the bucket remains private and no source receipt or real student record was copied.

## Cost and approval gate

No bucket has been created and no provider credentials have been configured by this setup. Check the selected provider's current pricing before creating storage or uploading any file. Do not enable a paid storage provider or incur charges without the owner's explicit approval. Hatchable remains the live service; this guide is for a separate preview only.
